# AI Usage Disclosure

AI tools are allowed. We want to know **how** you used them, because using them well is a
skill. Honest answers are never held against you. Discovering undisclosed use is.

## Tools used
- **Claude Code** (Anthropic's CLI agent, Claude Opus model). It worked directly in this
  repository: it read files, ran commands, and wrote code and tests.

## What I used them for
I worked through the assignment step by step with Claude Code. At each step I asked it to
explain what was needed first, then had it implement the step:

1. Comparing assignments A and B, and explaining what the data generator produces.
2. Writing the value parsers (`parsers.py`) and their tests.
3. Designing the Postgres schema, the PII approach (HMAC phone hash + Fernet encryption) and lead
   ingestion.
4. Building the append-only event ledger, including the idea of linking events to leads at read
   time so that late leads adopt earlier orphans.
5. The derived-facts SQL views (effective disposition, buckets).
6. The report writers.
7. The idempotency verification script, and profiling and optimising the large dataset.
8. Drafting `SUBMISSION.md` and `solution/README.md`.

Almost all of the code, tests and the first draft of the documentation were generated by the AI.

## What I wrote or decided myself
- **Chose assignment A** after asking for a comparison of the two.
- **Chose PostgreSQL over SQLite.** The AI recommended SQLite, mainly because it's zero-setup for
  reviewers. I chose Postgres, and first checked that port 5432 was free on my machine.
- **Decided not to use an ORM** after asking whether we needed models and weighing the trade-offs
  the AI laid out.
- **Set the order and scope of work** (parsers → leads → events → facts → reports → verification)
  and asked for each step to be explained simply before it was built.
- **Questioned the plan at each step instead of accepting it.** For example, I asked whether we
  needed ORM models, whether code had to live only in `solution/`, and whether the large dataset
  command was needed. I checked the answers against the assignment README.
- **Set up the multi-account Git/SSH workflow myself** (a separate SSH alias for my personal
  GitHub account) and created the private repo.
- **Asked for a status and "is it perfect?" check** before writing docs. That's how the ambiguous
  spec decisions were listed as risks in `SUBMISSION.md`.
- **Insisted on a full repo audit before pushing:** placeholders, secrets, generated data, and
  the remote, which was still pointing at the assignment owner's repo.


## Where the AI was wrong or unhelpful
- **The report crashed on the large dataset.** The first version worked on the small data, but
  on `--scale large` Postgres failed with `could not resize shared memory segment` (Docker's
  64 MB `/dev/shm` versus parallel hash joins). Found by actually running the large dataset.
  Fixed by disabling parallel query for the report session, because `docker-compose.yml` must
  stay unmodified.
- **The first SQL views were inefficient.** They scanned the ledger three times per call and
  twice per lead, so the large report took 24 s. They were rewritten as single-pass aggregations
  (14 s), and the output was checked to be byte-identical.
- **Lead ingestion was row-by-row,** two database round trips per row, which took about 17 s per
  28k-row file and put the large dataset over the 2-minute target (136 s total). It was rewritten
  to merge in memory and bulk-upsert (38 s total), and the output was checked to be identical.
- **A test refactor left an unused import behind**, which had to be cleaned up afterwards.
- **Explanations were too technical at first.** I had to ask for simpler explanations
  ("explain like I'm 15") of the lead ingestion, event ledger and derived-facts steps before I
  understood them.
- **It didn't do the performance work up front.** The slow views and row-by-row inserts were
  only fixed once the large dataset was actually run while writing the docs. Earlier steps were
  reported as "done" without that check.
- **It drafted `AI_USAGE.md` itself**, which I had to review.


## How I verified AI-generated code
- **Asked for a plain-language explanation of every step** (parsers, lead ingestion, ledger,
  derived facts) before moving to the next one, so I understood what each piece does and why.
- **Tests:** 148 pytest tests covering the rules most likely to break: phone normalisation,
  dates, effective disposition, buckets, idempotency, orphan adoption and PII.
- **Independent re-implementation:** the AI-written SQL was checked against separate plain-Python
  implementations computed straight from the raw files. The data-quality counts and all 1892
  leads' derived facts matched with 0 differences.
- **Spec examples:** the README's example values (`0.5625`, `2026-10-14T17:55:24+05:30`) appear
  in the seed-42 output.
- **Unseen seeds and orderings:** `solution/scripts/verify_idempotency.sh` on seeds 42 and 7,
  plus an end-to-end test on seed 1234 that loads all events before any leads.
- **Inspecting the database directly** with `psql`, to confirm no plaintext phones are stored
  and that the ledger rejects UPDATE/DELETE.
